## 4. 공유 셀에서 뒤집힌 2건 — 시간 placebo의 재추출

| 셀 | `screen_pass` | 등급 | `p_temporal_nw` |
|---|---|---|---|
| `ev_payout_yield\|ev_payout_yield\|bucket\|60\|120` | True → **False** | B → C | 0.0891 → **0.1287** |
| `mcap_krx_log\|mcap_krx_log\|cum\|0\|120` | False → **True** | C → A | 0.1386 → **0.0495** |

두 셀 모두 뒤집힌 게이트는 `temporal_null_pass` 하나이고, 나머지는 전부 비트 단위로 같다 — `ic_mean`, `p_nw`, `tradable_retention`, `nonoverlap_robustness_pass`, `offset_status`, `valid_subperiods`, `sign_consistent_subperiods`, `period_sign_pass` 모두 동일하다.

원인은 설계다. 시간 placebo의 순환 이동 거리가

```python
derive_replicate_seed(placebo_kind="temporal", replicate_index=..., config_hash=config_hash)
```

로 seed를 받으므로 **새 사전등록은 null을 새로 뽑는다.** 옛 계약의 null을 물려받지 못하게 하는 것이 목적이고, 교차검정 mapping(`mapping_seed_sequence`)도 같은 규칙이다. Phase A의 `permutation_cell_stats`가 7,500행 전부 다른 것도 이것 때문이다.

문제는 문턱이다. `temporal_long_cell_repeats = 100`, `temporal_p_max = 0.10`인데, p ≈ 0.1에서 100회 재추출의 표준오차는 `sqrt(0.1×0.9/100) ≈ 0.030`이다. 관측된 흔들림(0.0891 → 0.1287은 replicate 4개, 0.1386 → 0.0495는 9개)은 **1~3 표준오차 안**이다.

즉 이 두 셀은 **100회로는 시간 placebo 판정이 갈리지 않는 경계 셀**이다. 실체가 바뀐 것이 아니다. 두 건이 서로 반대 방향이라 `screen_pass` 총계에는 순변화가 없다(53 + 32 = 85).

→ **F-9.11로 남긴다**: 문턱 근처 셀은 replicate를 늘리거나 Monte Carlo 구간을 같이 보고해야 한다. 지금 상태로는 경계 셀의 `screen_pass`가 층마다 흔들린다.

## 7. Phase B가 한 번 죽었다 — 계약 스탬프

첫 시도(05:38)가 첫 마트에서 멈췄다.


A0 마트는 `analysis_config_hash = 3ca949e6`이 찍혔지만, Phase B 마트 9개는 `compute-all --features`와 두 리포트 스크립트가 만들어 **전부 `None`**이었다. `run_phase_b_core`는 이 값을 스캔 config 해시로 고정하므로 `_cache_contract_matches`가 거부한다 — 바뀐 사전등록이 다른 규칙으로 만든 마트를 조용히 재사용하지 못하게 하는 가드이고, **옳은 거부다.**

**메타데이터를 편집하지 않았다.** 스탬프만 채워 넣으면 계약의 존재 이유가 사라진다. run이 호출하는 것과 같은 `register_phase_b_marts`를 `force=True`로 돌려 13개를 정상 재빌드했다(34분). `dim_peer_monthly`는 11,292,902행 / 232 월말로 이전과 동일하게 나왔다.

08-23 라운드에 이 단계가 없었던 이유는 그때 Phase B run이 자기 마트를 직접 만들어 스탬프가 처음부터 맞았기 때문이다.

**→ 2026-09-09 고쳤다 (F-9.12).** `register_phase_b_marts`가 계약 불일치를 재빌드로 처리한다. `--force` 플래그를 붙이는 쪽은 택하지 않았다 — 사람이 미리 알아야 하고, 이미 맞는 마트까지 전부 다시 만든다. 지금은 불일치한 것만 다시 만든다.

`research/etl/mart.py`에 `StaleMartContract(RuntimeError)`를 두고 9개 raise 자리를 옮겼다. 메시지 문자열로 구분하면 문구가 바뀔 때 조용히 안 걸린다. `RuntimeError` 하위라 기존 핸들러와 테스트는 그대로 동작한다. `register_mart_view`의 raise도 같은 타입이지만 **동작은 안 바꿨다** — A0 마트 bind에서 불일치하면 A0와 Phase B의 config가 다르다는 뜻이라 죽는 것이 맞다.

`force=True`를 중간에 끊으면 마트가 빈다(`materialize`가 쓰기 전에 `rmtree`한다). 이 검증 중에 `feat_fin_scan_daily`를 그렇게 날려 다시 만들었다. 발행된 run 산출물은 별도 디렉터리라 무사했다.
